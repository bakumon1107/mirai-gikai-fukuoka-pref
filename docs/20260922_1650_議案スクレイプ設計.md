# 議案スクレイプ設計（福岡県議会 公式サイト）

作成日: 2026-09-22

福岡県議会ホームページ（`www.gikai.pref.fukuoka.lg.jp`）から提出議案と採決結果を
取得し、`bills` テーブルへ投入するまでの設計。

---

## 1. 背景

### 現状の課題

| 項目 | 現状 |
| --- | --- |
| 議案データ | **令和8年6月定例会の33件のみ**。`packages/seed/fukuoka/bills-r8-6gatsu-data.ts` に手書き |
| 取得元 | 議案付議案件一覧PDF（`docs/data/202607111221.pdf` 等）を人が読んで転記 |
| 議決結果 | 全件 `"approved"` 固定 |
| 原文リンク | `bills.source_url` カラムは存在するが未設定 |
| 更新契機 | 定例会ごとに人が気づいて手作業 |

`seed-bills.ts` の該当箇所:

```ts
// bills.status（bill_status_enum: preparing/submitted/in_committee/plenary_session/approved/rejected）
// ※ 議決結果はPDFに無いが、知事提出議案は通常可決のためユーザー判断で "approved"。
const DEFAULT_STATUS = "approved" as const;
```

議決結果を推測で埋めているため、否決・継続審査・撤回が発生した場合にサイトが
事実と異なる表示をする。また9月定例会（約40件）は未投入のままである。

### 本対応で解決すること

1. 議決結果を公式の採決結果ページに基づいて設定する（推測からの脱却）
2. カバレッジを1会期から令和7〜8年の10会期へ拡大する
3. PDF転記という品質リスクの高い手作業を排除する
4. `source_url` に公式ページへのリンクを設定する

### 本対応で解決しないこと

- **`bill_contents`（難易度別のわかりやすい本文）の生成**は従来どおりAI生成＋
  ユーザー確認フローのまま。本設計は「素材を自動で揃える」までを担う。
- 一般質問は**別PRに分離**する（後述）。

## 3. 法務・運用上の前提

事前調査の結果、本スクレイプは以下の前提で実施する。

- 議会公式サイトの[免責事項等](https://www.gikai.pref.fukuoka.lg.jp/soshiki/2/menseki.html)には
  「著作権は原則として福岡県に帰属します」とあるのみで、**複製・転載を禁止する文言はない**
  （禁止文言があるのは中継サイト `fukuoka-pref.stream.jfit.co.jp` のみ）。
- `robots.txt` は `Disallow: /giin/` のみ。**議案・採決ページは Allow**。
- 取得するのは議案番号・件名・提出日・採決結果といった**事実情報**であり、
  配列も議案番号順で機械的なため編集著作物性も認めにくい。

### 遵守事項

- **リクエスト間隔 2秒**（`scrape-committee-minutes.ts` と同じ）。429/503 はリトライ。
- User-Agent に連絡先を明記する。
- `source_url` で**必ず公式ページへリンク**する。原文の丸ごとミラーはしない。
- **`/giin/` 配下（議員名簿）は取得しない**（robots.txt で明示的に Disallow）。

## 4. 取得対象の実データ構造

### 4.1 年次索引（`list43.html` → `list43-*.html`）

URL を推測せず、索引ページを辿って取得対象を決定する。
`gian-3102.html`（平成31年2月）のように元号をまたぐ命名があり、推測は破綻するため。

```
list43.html
  ├─ list43-216.html  令和8年   → gian-0809 / 0808 / 0806 / 0802
  ├─ list43-205.html  令和7年   → gian-0712 / 0709 / 0706 / 0705 / 0704 / 0702
  └─ …（令和6年以前。今回は対象外だが索引構造は同一なので後から範囲を広げられる）
```

リンクテキストが `令和7年6月定例会の提出議案件名` の形式なので、
**会期名はここから取る**（`gian-*.html` 本文の見出しとも一致する）。

### 4.2 提出議案ページ（`gian-*.html`）

```
令和8年9月定例会の提出議案件名
令和8年9月9日提出                      ← 提出日見出し
第122号議案　令和8年度福岡県一般会計補正予算（第3号）
第123号議案　福岡県職員の勤務時間、休暇等に関する条例の一部を改正する条例の制定について
…
令和8年9月17日提出                     ← 同一ページ内に複数の提出日
第158号議案　令和8年度福岡県一般会計補正予算（第4号）
…
議員提出                               ← 種別セクション
第3号議案　地方自治法第100条の2の規定に基づく専門的知見の活用についての議決内容の一部変更について
```

**注意点:**

- **提出日見出しが複数ある**。直近の見出しをその後の議案に適用する。
  ただし `gian-0705`（令和7年5月臨時会）のように**提出日見出しが無いページもある**。
- **「議員提出」「委員会提出」セクションは番号体系が別**。
  知事提出の「第3号議案」と議員提出の「第3号議案」が同一会期に共存しうる。
- **件名が `<br>` で改行される例がある**。実測:

  ```
  第131号議案　専決処分について（令和8年度福岡県一般会計補正予算
  ）
  ```

  タグ除去後に行結合してから議案番号でトークナイズすること。
  行単位で素朴にパースすると件名が途中で切れる。

### 4.3 採決結果ページ（`saiketsu-*.html`）

**個別議案ごとの結果表ではなく、レンジ宣言文＋議案一覧**という構造。

```
令和7年12月定例会の採決結果
令和7年12月19日、第188号議案から第226号議案の39件については、
いずれも原案のとおり可決または同意されました。
第188号議案　令和7年度福岡県一般会計補正予算（第4号）
…
```

宣言文のバリエーション（実測）:

| 会期 | 宣言文 |
| --- | --- |
| 令和7年12月 | `第188号議案から第226号議案の39件については、いずれも原案のとおり可決または同意されました。` |
| 令和7年2月 | `第20号議案、第21号議案については、いずれも原案のとおり可決されました。`<br>`第1号議案から第19号議案、第22号議案から第79号議案の77件及び委員会提出議案第2号議案、第3号議案の2件については、いずれも原案のとおり可決または同意されました。` |
| 令和元年6月 | `第67号議案から第109号議案、委員会提出第1号議案については、いずれも原案のとおり可決・承認または同意されました。` |
| 令和8年9月（会期中） | `令和8年9月17日、議員提出第3号議案については、原案のとおり可決されました。`<br>`令和8年9月18日、第158号議案については、原案のとおり可決されました。` |

**ここが本設計の最大の制約:**

1. **結果が束ねられている**。「可決または同意」「可決・承認または同意」という表現では、
   個別議案が可決か同意か承認かを**判別できない**。
2. **レンジ表現の解析が必要**。「第188号議案から第226号議案」「第20号議案、第21号議案」
   「委員会提出議案第2号議案、第3号議案」が混在する。
3. **ページ自体が欠損しうる**。`saiketsu-0705` は 404（`gian-0705` は存在する）。
4. **会期中は逐次追記される**。令和8年9月は2件しか記載がなく、残りは未採決。

したがって本設計が取れるのは「**可決レンジに入っているか否か**」であり、
個別の議決種別ではない。価値は**レンジから漏れた議案を検出して人に上げる**点にある。

## 5. データモデルへのマッピング

### 5.1 `bills` テーブル

```ts
{
  name: string,                      // 件名（「第122号議案　」を除いた部分）
  bill_number: string,               // 「第122号」形式（既存データと揃える）
  bill_type: "bill" | "member_bill", // 知事提出 / 議員提出・委員会提出
  status: BillStatusEnum,            // §5.2 参照
  status_note: string | null,        // 採決結果の原文と判定根拠
  publish_status: "draft",           // ユーザー指示により draft 固定
  council_session_id: uuid,
  source_url: string,                // 公式ページへのリンク
}
```

既存の複合ユニーク制約がそのまま冪等キーとして使える:

```sql
-- supabase/migrations/20260405150000_add_bill_type.sql
CREATE UNIQUE INDEX bills_session_number_type_unique
  ON bills (council_session_id, bill_number, bill_type)
  WHERE bill_number != '';
```

`(council_session_id, bill_number, bill_type)` で upsert すれば、
知事提出「第3号」と議員提出「第3号」の衝突も起きない。**マイグレーションは不要**。

`bill_type` の判定:

| ページ上の表記 | `bill_type` |
| --- | --- |
| （セクション見出しなし＝知事提出） | `bill` |
| `議員提出` | `member_bill` |
| `委員会提出` | `member_bill` |

> 意見書・決議（`opinion` / `resolution`）は `gian-*.html` の本文からは種別を
> 判別できないため、今回は `member_bill` に寄せる。件名に「意見書」「決議」を
> 含む場合の細分化は将来課題とする（§9）。

### 5.2 `status` の決定ロジック

`bill_status_enum` は
`preparing / submitted / in_committee / plenary_session / approved / rejected / adopted / partially_adopted / reported`。

| 条件 | `status` | `status_note` |
| --- | --- | --- |
| 採決結果の可決レンジに含まれる | `approved` | 宣言文の原文をそのまま格納 |
| 採決結果ページはあるが、どのレンジにも含まれない | `submitted` | `採決結果ページに記載なし（要確認）` |
| 採決結果ページが404（例: 令和7年5月臨時会） | `submitted` | `採決結果ページ未掲載` |
| 会期が進行中で未採決 | `submitted` | `会期中（未採決）` |

**`approved` 以外を機械的に確定させない**のが要点。「レンジ外＝否決」ではなく、
「レンジ外＝人が確認すべき対象」として扱う。スクレイプ実行時にレンジ外議案を
サマリ出力し、目視レビューの入口にする。

### 5.3 `council_sessions`

`bills.council_session_id` の解決には会期レコードが必要。

```ts
// council_sessions の実カラム
{ id, name, slug, start_date, end_date, is_active, council_url }
```

既存の `seed-bills.ts` は会期名（`"令和8年 6月定例会"`）で検索している。
**公式サイトの表記は `令和8年6月定例会`（スペースなし）で、既存DBの表記と異なる**点に注意。
正規化（スペース除去＋全角半角統一）して突合し、**見つからない会期はスクリプトを
中断してユーザーに報告する**（会期の自動作成はしない。`start_date` 等を推測で埋めると
サイトの会期表示が壊れるため）。

> **未確認事項**: 本番DBに令和7年の各会期レコードが存在するかは未検証
> （本番DB参照が権限で実行できなかった）。実装着手前に `council_sessions` を
> 確認し、不足分の作成方針をユーザーと決める。→ §9

## 6. パイプライン

既存の委員会議事録スクレイプ（`scrape-committee-minutes.ts`）と同じ形に揃える。

```text
① スクレイプ   scrape-bills.ts          → docs/data/bills/<会期slug>.json（中間JSON）
② 目視レビュー （ユーザー）               ← レンジ外議案・パース警告を確認
③ seed        seed-bills-from-scrape.ts → bills（publish_status = draft）
④ AI本文生成   既存フロー                → bill_contents
⑤ ユーザー確認（必須・CLAUDE.md規約）
⑥ 公開        publish_status を published に更新
```

②を独立させるのはユーザー指示（「とりあえずDraftにして、目視レビューを別途させて」）による。
③は `draft` で投入するため、レビュー前にサイトへ露出しない。

### 中間JSONの形式

```jsonc
{
  "sessionName": "令和8年9月定例会",
  "sourceUrl": "https://www.gikai.pref.fukuoka.lg.jp/site/honkaigi/gian-0809.html",
  "voteResultUrl": "https://www.gikai.pref.fukuoka.lg.jp/site/honkaigi/saiketsu-0809.html",
  "scrapedAt": "2026-09-22T16:50:00+09:00",
  "bills": [
    {
      "billNumber": "第122号",
      "billType": "bill",
      "name": "令和8年度福岡県一般会計補正予算（第3号）",
      "submittedDate": "2026-09-09",
      "status": "submitted",
      "statusNote": "会期中（未採決）"
    }
  ],
  "warnings": ["第131号: 件名に改行が含まれていたため結合した"]
}
```

中間JSONを挟むことで、②のレビューがDBに触らずにできる。
また再実行時の差分確認もファイル比較で済む。

## 7. 実装ファイル構成

`packages/seed/fukuoka/` 配下。CLAUDE.md の
「純粋関数は `utils/` に切り出し、テスト必須」に従い、
**HTTP通信を伴わないパース処理をすべて純粋関数として分離**する。

```
packages/seed/fukuoka/
├── parse-bill-index.ts          # list43*.html → 対象ページ一覧      【純粋関数】
├── parse-bill-index.test.ts
├── parse-bill-list.ts           # gian-*.html → 議案配列              【純粋関数】
├── parse-bill-list.test.ts
├── parse-vote-results.ts        # saiketsu-*.html → 可決レンジ        【純粋関数】
├── parse-vote-results.test.ts
├── expand-bill-number-range.ts  # 「第188号議案から第226号議案」→ [188..226] 【純粋関数】
├── expand-bill-number-range.test.ts
├── scrape-bills.ts              # ①エントリポイント（HTTP・2秒ウェイト）
├── seed-bills-from-scrape.ts    # ③DB投入
└── __fixtures__/
    ├── gian-0809.html           # 提出日見出し複数＋議員提出＋改行件名
    ├── gian-0705.html           # 提出日見出しなし
    ├── saiketsu-0712.html       # 単一レンジ
    ├── saiketsu-0702.html       # 複数宣言文＋委員会提出
    └── list43-216.html
```

fixture は実際のページを保存して使う（`scrape-committee-minutes` と同じ方針）。
モックは使わず、HTMLを入力として純粋関数を直接テストする。

### `expand-bill-number-range` の仕様

宣言文の解析で最も壊れやすい箇所なので独立させる。

```ts
/** 採決結果の宣言文から、可決扱いの議案番号を展開する。 */
export function expandBillNumberRange(sentence: string): {
  bill: number[];        // 知事提出議案の番号
  memberBill: number[];  // 議員提出・委員会提出議案の番号
}
```

テストケース（実データから）:

| 入力 | 期待 |
| --- | --- |
| `第188号議案から第226号議案の39件` | `bill: [188..226]`（39件であることも検証） |
| `第20号議案、第21号議案` | `bill: [20, 21]` |
| `第1号議案から第19号議案、第22号議案から第79号議案の77件` | `bill: [1..19, 22..79]`（77件） |
| `委員会提出議案第2号議案、第3号議案の2件` | `memberBill: [2, 3]` |
| `議員提出第3号議案` | `memberBill: [3]` |

**「N件」という件数表記が併記されている場合は展開結果の件数と照合し、
不一致ならパースエラーとして落とす**。静かに壊れるのを防ぐ
（沼津版の `discussvision-client.ts` が Zod で同じことをしている）。

## 8. 既存資産との関係

### 8.1 `bills-r8-6gatsu-data.ts`（令和8年6月・33件）

令和8年6月定例会は**スコープに含まれるため既存データと重複する**。

- 既存レコードは `(council_session_id, bill_number, bill_type)` で一致するため、
  upsert すれば重複行は作られない。
- **`bill_contents`（AI生成済みの本文）を絶対に壊さないこと**。
  `seed-bills-from-scrape.ts` は `bills` の事実カラムのみ更新し、
  `bill_contents` には一切触れない。
- 既存33件は `publish_status = published` で公開済み。
  **スクレイプ由来の更新で `publish_status` を上書きしない**
  （新規行のみ `draft`、既存行は現状維持）。

この会期は**回帰テストの基準として使える**。スクレイプ結果の議案番号・件名が
既存33件と一致することを確認すれば、パーサーの正しさが実データで裏付けられる。

### 8.2 PDF由来データの扱い

`bills-r8-6gatsu-data.ts` は PDF から `category`（分類）と `department`（所管課）と
`gaiyou`（概要）を持っているが、`seed-bills.ts` の `billRow` を見ると
**いずれもDBに保存されていない**（dry-runのログ出力に使われているのみ）。

```ts
const billRow = {
  name: bill.name,
  bill_number: bill.billNumber,
  bill_type: BILL_TYPE,
  status: DEFAULT_STATUS,
  publish_status: DEFAULT_PUBLISH_STATUS,
  council_session_id: session.id,
};
```

したがって **HTMLスクレイプへの切り替えでデータは劣化しない**。
`gian-*.html` は議案番号・件名・提出日を持ち、PDFにしかない情報は
現状DBに入っていない情報である。

### 8.3 `seed-bills.ts` の扱い

既存スクリプトは削除せず残す（令和8年6月の再現性を保つため）。
新スクリプトは別ファイル（`seed-bills-from-scrape.ts`）として追加し、
`DEFAULT_STATUS` による推測ロジックは新スクリプトには持ち込まない。

---

## 9. 未決事項・確認が必要な点

実装着手前にユーザーと確認する。

1. **`council_sessions` の既存行**
   令和7年の各会期（2月・4月臨時・5月臨時・6月・9月・12月）のレコードが
   本番DBに存在するか未検証。不足している場合、会期を新規作成するのか、
   スクレイプ対象から外すのかを決める必要がある。
   （本調査では本番DB参照が権限で実行できなかった）

2. **「可決または同意」の粒度**
   個別議案の議決種別が判別できないため、レンジ内は一律 `approved` とする。
   サイト表示上これで許容できるか。`status_note` に原文を格納するので
   UI側で補足表示する余地はある。

3. **令和8年6月の既存33件を上書きするか**
   §8.1 の方針（事実カラムのみ更新、`bill_contents`・`publish_status` は保持）で
   問題ないか。

4. **意見書・決議の細分化**
   `bill_type` の `opinion` / `resolution` は今回使わない。
   件名からの判定を入れるかは将来課題。

5. **定期実行**
   今回は手動実行スクリプトとして作る。会期中の差分取り込みを
   cron 等で自動化するかは別途判断。

pnpm --filter seed test   # 純粋関数のテスト（fixture ベース）
